## Verdict

The proposed Laravel/Blade/Tailwind architecture and vertical-slice order are suitable for the supplied portal. Explicit legacy mappings, private storage, policy-enforced ownership, InnoDB transactions, preserved hashes/IDs, and events separate from delivery are the correct foundation. The route audit correctly distinguishes unsafe grants and broken/missing handlers from intended feature parity.

**Ready as a corrected planning baseline; not ready to declare M0 complete or begin a production migration.** M2 has now completed the isolated restore and byte reconciliation. Source completeness, business choices below and hosting facts remain unresolved. This technical review is not user approval of proposed workflow changes or authorization to implement beyond requested milestones.

## Review findings and corrections

| Review ID / severity | Finding | Resolution in the documentation |
| --- | --- | --- |
| RV1 High | Laravel's default queue table `jobs` can collide with legacy `Jobs` on a case-insensitive MySQL configuration; default scaffold `users` can similarly collide with `Users`. A database queue must never write payloads into contractor Jobs. | Reserve legacy table names case-insensitively. Adapt the default auth migrations to Users and configure a separate `app_queue_jobs` table plus named ancillary tables before running generated migrations. Check lower_case_table_names in local/test/hosting environments. Added to schema, plan and tests. |
| RV2 High | The notification requirement applied verified-address gating to all mail. That would prevent first verification and proof of a changed email. | Verification/invitation/recovery have narrowly scoped unverified-address exceptions with signed/tokenized, throttled links. They grant no job access. Ordinary workflow messages use validated eligible addresses. Corrected event requirements. |
| RV3 Medium | After-commit dispatch prevents early delivery but does not by itself retain intent if dispatch fails after the mutation commits. SMTP retries also cannot promise exactly-once mailbox delivery. | Require durable intent saved with mutation/audit, recoverable delivery processing, per-recipient/channel attempt tracking and duplicate-intent suppression. Queue after commit; document possible ambiguous external send and avoid claiming exactly-once delivery. |
| RV4 High | Proposed archive-first behavior could silently remove existing admin hard-delete capabilities, contrary to feature preservation. Reassignment/terms reconfirmation also introduce business changes. | Retain guarded delete capability or obtain an explicit accepted replacement; default to non-destructive archive, restrict referenced history and define retention. Mark transition/visibility changes as recommendations for product review, not established legacy behavior. |
| RV5 Medium | Route paths were illustrative and did not state how production's `/contractors/` prefix, assets, signed links and sessions will work. No .htaccess or deployment descriptor was recovered. | Treat `/contractors/` as an external base path unless deliberately changed. Serve only Laravel public/index.php, keep source/secrets/private storage outside the public tree, verify base-path URLs and use a dedicated session cookie. Hosting rewrites/aliases remain to be confirmed. |
| RV6 Medium | The plan did not distinguish recoverable missing third-party assets from missing business handlers or specify ID/foreign-key compatibility for scaffold tables. | Missing PHPMailer/Bootstrap/TinyMCE assets are evidence limits, not dependencies of the Laravel replacement. Missing note/accept/download handlers need explicit semantics. Any actual FK to Users/Jobs must match legacy signed INT keys and custom column names; do not blindly create users.id/bigint references. |
| RV7 Medium | Imported records could be accidentally rejected by new registration rules, verified-email assumptions, HTML cleanup or event hooks. | Preserve source rows in staging, import through dedicated mapping rather than public FormRequests, report exceptions, keep original HTML/bytes/history available, and suppress review/mail events. Apply new rules deliberately to future mutations, not silently to historical imports. |

RV1 is an inference from the actual `Jobs`/`Users` names, Laravel's database-queue scaffold and MySQL identifier rules; it is not an observed collision in a restored local database. [MySQL identifier case sensitivity](https://dev.mysql.com/doc/refman/8.0/en/identifier-case-sensitivity.html), [Laravel database queues](https://laravel.com/framework/docs/queues#database).

Laravel provides transaction-aware dispatch and verification support; durable-intent/outbox and recipient rules here are application design decisions. [Laravel queue transaction behavior](https://laravel.com/framework/docs/queues#jobs-and-database-transactions), [email verification](https://laravel.com/framework/docs/verification). Serving only the public front controller follows [Laravel deployment guidance](https://laravel.com/framework/docs/deployment#nginx); the specific subdirectory configuration is still a hosting question.

## Recommended decisions D1–D10

These are concrete recommendations from the original review, with D1 updated to the subsequent user selection. D2–D10 remain proposed until accepted; mandatory ownership, approval, validation and anti-spam requirements follow AGENTS.md. Intentional differences are recorded alongside tests.

| Decision | Recommended rule | Remaining consequence or fact |
| --- | --- | --- |
| D1 — Approval/onboarding | **User selected status/email verification only for pending contractors.** Status/logout/verification are available after login; profile/services/documents/jobs and private work routes require approval=1 and verified email. Review state=2 suspends protected work access. Imported accounts retain hashes and are not automatically verified. | M3 enforces this access selection. The imported-verification question was unanswered; the existing verification requirement/default applies to all imported roles. Inform users/admins and resolve any explicit rollout exception before release. |
| D2 — Notes | Account Notes remain admin-private. Shared Job_Notes are visible to the current authorized assignee. Permit append-only contractor questions/notes on their pending or accepted assigned job; media alone requires acceptance. Completed jobs are contractor read-only. No contractor edit/delete or private-note capability is inferred. | Pre-acceptance notes preserve the intent of an always-present note form, but the original handler is absent. Post-completion restriction is a proposed change. |
| D3 — Jobs/evidence | Admin completes/reopens. Accept only assigned pending jobs; repeat requests keep original time. Reassignment/unassignment resets current acceptance/completion dates and flags while retaining transition history. A completed job must first be explicitly reopened before reassignment. Reopen with the same assignee retains acceptance, clears active completion and logs prior completion. Do not transfer consent; an admin can explicitly accept on behalf again. | Recommend material scope/terms/price/deposit/material-responsibility changes require new acceptance; completed material edits require reopen. Do not silently reset a historical acceptance or fabricate its actor/terms version. Define which other changes require reconfirmation. |
| D4 — Eligibility/matching | Preserve ANY-service suggestions and ALL-selected-service directory search. Assign active approved contractors only; do not let an approval override grant unapproved work access. An admin may assign an approved contractor outside service suggestions with a logged reason. | Matching is a suggestion, not proof of qualifications. Admin-managed contacts without verified email can remain assigned records, but gain no contractor web access until verification. |
| D5 — Uploads/review | Job media JPEG/PNG/PDF ≤10 MiB per file. Propose documents PDF/JPEG/PNG ≤5 MiB for both roles; photos JPEG/PNG/GIF ≤5 MiB with decoded-image dimension limits and safe derived previews. Keep original imported files intact. Self profile/photo/services changes re-review; unchanged submissions and document-only uploads do not automatically revoke approval. | Profile/doc caps and photo/document review behavior are changes needing acceptance. GIF support need not imply animated previews. W9/Insurance/Other types remain; expired/NULL expiry are explicit display states. |
| D6 — Retention/visibility | Archive/disable accounts by default; preserve all job and actor history, including orphan logs. Keep an explicit, separately confirmed admin delete route with reference checks; do not redefine DELETE as archive invisibly. Archive prior document on replacement, no silent BLOB deletion. Block removal of services used by either pivot. Current assignee sees shared job history; former assignee loses private access. | Hard-purge eligibility/retention periods and whether prior assignee media is confidential require owner decisions. If narrower historical visibility is chosen, add schema; existing notes/media have no visibility flag. |
| D7 — Notifications | All required business events are centrally configurable. Recommended initial defaults: enabled after the local-mail test gate, admins receive registration/re-review/acceptance, affected contractor receives approval/assignment/job changes/completion, and counterpart receives shared notes/media. Exclude author and batch uploads. Security verification/recovery cannot be muted as ordinary preferences. Run active-insurance reminders daily at 30 days and expiry, with one catch-up for files entering the window late. | No import-triggered/backfill email. Confirm actual admin recipients/sender and defaults before real delivery. Record document/version/reminder-stage uniqueness; skip archive/NULL expiry; choose business timezone for scheduler. |
| D8 — Accounts/abuse | Preserve nullable-email managed contacts without login. Keep controlled admin password-setting parity and offer secure invitation/recovery; invalidate relevant sessions and audit actor without exposing passwords. Registration uses server-verified bot protection, layered throttles, duplicate email enforcement and review signals, never automatic deletion by heuristic. | Bot provider/hosting secrets, risk retention, admin recovery/MFA and numeric limits need configuration. Recovery/verification must not accidentally activate archived/blocked users. Existing hashes are retained; no blanket password reset. |
| D9 — Money/dates/content | Decimal-preserving nonnegative amounts, zero distinct from NULL, deposit ≤approved price on create/edit. Propose a positive deposit requires a known approved price. Keep originals in staging and sanitize rendered HTML with a documented formatting allowlist. Compare due/expiry as business calendar dates. | Currency and business timezone must come from owner/hosting evidence, not the audit timezone or dollar icon. The deposit-without-price restriction and HTML allowed elements need product acceptance. Verify source encoding before conversion. |
| D10 — Readiness/hosting | Select Laravel/PHP/Tailwind after runtime checks; private storage and a durable database intent mechanism are baseline, workers/scheduler based on hosting. Complete isolated restore and relevant missing-behavior investigation before claiming M0 complete. Do not require legacy third-party libraries to run Laravel. | Obtain current consistent source/data before cutover, host/public-root/subpath/queue/scheduler/SMTP facts and private credential rotation. The review authorizes none of those production actions. |

## Implementation and release gates

1. **Current stop:** M1/M2/M3/M4/M5 are complete locally under subsequent user instructions. [M5 evidence](m5-jobs-notes-media.md) records the job, note, media, transition and guarded-deletion slice. Stop before M4.5 business notifications, M6 dashboards/templates, M7 native review or production work until requested; this does not accept the remaining decisions.
2. **M0 completion:** validate local restore, counts, encoding, binary round trips and orphan handling; resolve missing business behavior or document accepted replacements. Missing third-party assets can remain a recorded limitation when their features are adequately understood; never claim a complete source download without a source manifest comparison.
3. **M1/M2 when requested:** create the separate app and explicitly adapted migrations; validate case-safe table naming, exact legacy auth/key mapping, actual MySQL behavior and repeatable import. Some nonblocking preferences such as additional reminder offsets can stay deferred until their slice; identity/storage/state decisions must precede dependent code.
4. **M3–M6:** implement minimal service catalog, identity/approval/abuse controls, contractors/files, jobs/collaboration and management/dashboards. Add domain audit/intents and phone accessibility in each slice. No broad frontend rewrite without route parity checks.
5. **M7/M8:** direct permission/state/storage/event tests, real import reconciliation and recorded device checks; then a separately reviewed rollout with current backup, secret rotation, rollback and mail/queue/scheduler health. Static PHP lint and SQL parsing are not release tests.

Remaining factual blockers: business timezone/currency, host runtimes and public routing, SMTP/admin recipients, scheduler/worker support, source completeness/current export and retention policy. Workflow recommendations above are ready for product acceptance; they have not been silently marked approved by this review.
